# Message bounds

Every variable-length field of a message the firmware carries needs a fixed
capacity before code is generated, and this page says where that capacity comes
from, what happens when nobody states one, and how to change it.

## Why a bound exists

The MCU has no heap and no variable-size storage. A `string` field becomes
`char name[N + 1]`, a `T[<=N]` field becomes an array plus a count, and `N` is
what makes the struct a fixed size at compile time. The bound is therefore part
of the firmware's memory picture, not part of the ROS interface: it never
travels on the wire and the host never learns it. The serializer refuses a
value past the bound instead of truncating it, and the host's own copy of the
message keeps its unbounded ROS definition.

## Where a bound comes from

A variable-length field takes its bound from exactly one place, in this order:

1. **Its own `.msg` definition.** `string<=12 text` bounds the string; `float32[<=6]
   position` bounds the sequence. This is the normal case and the recommended
   one, because the definition and the storage can never disagree.
2. **A list beside the type**, for definitions the developer cannot edit. That
   is `bounds` in `r2s.yaml` for `r2s-gen generate`, or `--bound
   package/msg/Type.field=N` for `r2s-gen types`, or the same entry in a
   `r2s-types.yaml` type list.

Bound the field in the `.msg` whenever the definition is yours. The override is
for a package published by somebody else, where the storage the MCU needs is a
decision that package never made.

## What happens with no bound

Generation fails and names the field, rather than picking a capacity nobody
chose:

```text
r2s-gen: error: std_msgs/msg/Header.frame_id: unbounded string; set bounds['std_msgs/msg/Header.frame_id']; see https://apojomovsky.github.io/ros2serial/message-bounds.html
r2s-gen: error: sensor_msgs/msg/JointState.name: unbounded sequence; set bounds['sensor_msgs/msg/JointState.name'] to its element count; see https://apojomovsky.github.io/ros2serial/message-bounds.html
```

There is no fallback and no default. `wstring` and `wchar` have no wire form
here, so a field of either type fails the same way.

## The conflict rule

An override on a field the `.msg` already bounds is an error in both
directions, naming the field and the file that bounds it:

- A **tighter** bound under-holds a message the host may legally send, so a
  valid ROS message becomes a decode error on the MCU.
- A **looser** bound accepts a message ROS itself considers malformed.

Neither is silently accepted, and the same rule covers a sequence of strings,
where the pair is `[count, string_bound]` (`[6, 16]` reads "six names of up to
16 characters"). The bundled library is no exception: every field it needs is
named in `BUNDLE_BOUNDS`, which is why its limits are somebody's choice rather
than the definitions'.

## The built-in types' limits

The bundled Arduino library ships storage it chose, and those numbers may not
be what a message's fields lead you to expect: a `std_msgs/msg/String` carries
16 characters, `JointState` holds six joints, and `TFMessage` one transform.
Check them before relying on one:

```sh
ros2 run r2s_gen r2s-gen limits
```

Each row names the field, the storage it resolves to, and whether
`BUNDLE_BOUNDS` or the `.msg` supplied the capacity, so a limit the library
chose is told apart from one the definition states. A run prints one distro's
table; ask for another with `--distro lyrical` or `--distro rolling`. The table

## Overriding a built-in type's bound

The bundled library's capacities are compiled into its descriptors, so an
override is a **different library**, not an edit of that one. Generate your own
from the type and the bound you want:

```sh
ros2 run r2s_gen r2s-gen types std_msgs/msg/String \
  --bound std_msgs/msg/String.data=64 --out firmware/lib
```

The library's name carries the digest of its types and bounds
(`ros2serial_types_<digest>`), so it never collides with the stock
`ros2serial` library and Arduino cannot silently pick the wrong one. Point the
sketch at that tree instead of the bundled library, as the
[type library route](custom-interfaces.md#emit-a-type-library-for-the-x-macro-and-runtime-routes)
describes, and keep its copy current: the type hashes travel with the library,
and a stale copy makes the bridge reject every topic at handshake.

Changing a bound changes RAM, never the wire format, so the host side needs no
matching change and the bridge accepts a firmware built with any capacity.
